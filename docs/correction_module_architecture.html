Projet M2 - Développement et Déploiement d'un Système de Correction Pédagogique

📋 Contexte et Objectifs

Cadre du Projet

Ce document présente l'architecture technique d'un système de correction automatique d'électrocardiogrammes (ECG) développé dans un contexte de formation médicale. L'objectif est de fournir aux étudiants un retour immédiat, personnalisé et pédagogiquement pertinent sur leurs analyses d'ECG en texte libre.

Définition : Correction d'ECG

La correction d'ECG désigne ici le processus d'évaluation automatique de l'interprétation clinique d'un électrocardiogramme rédigée par un étudiant. Le système :

  1. Parse les réponses en langage naturel ("rythme sinusal avec BAV du 1er degré")
  2. Extrait les concepts cliniques mentionnés (rythme, conduction, morphologie)
  3. Aligne ces concepts avec une ontologie médicale de référence (281 concepts structurés)
  4. Attribue une note selon une grille explicite et reproductible
  5. Génère un feedback détaillé : points corrects, manques, erreurs, conseils ciblés

Objectif du M2 : Fiabilisation et Développement

La fiabilisation et le développement du prototype comprennent les axes suivants :

  • ✅ Interface utilisateur robuste : Application web Streamlit pour étudiants et enseignants
  • ✅ Streamlining du pipeline : Intégration fluide des 4 étapes (extraction → matching → scoring → feedback)
  • ✅ Déploiement local sécurisé : Solution on-premise pour la protection des données médicales
  • ✅ Performance optimisée : Réduction latence (<10s par correction) et gestion parallèle
  • ✅ Maintenabilité : Architecture modulaire, tests automatisés, documentation technique
  • ✅ Évaluation pédagogique : Études de fiabilité (concordance humain-machine) et d'acceptabilité

Stack Technologique

Prototype Actuel (Python)

  • Backend : Python 3.11 (owlready2, OpenAI API, Streamlit)
  • Ontologie : OWL 2.0 + raisonnement symbolique
  • LLM : GPT-4o / GPT-4o-mini (OpenAI)
  • Déploiement : Local / Heroku (dev)

Évolution Future (Production)

Pour un déploiement à grande échelle et en ligne, migration envisagée vers :

  • Backend : Java (Spring Boot) ou Node.js (Express) pour robustesse et scalabilité
  • Frontend : React.js / Vue.js pour interface réactive
  • API : REST/GraphQL pour intégration LMS universitaires
  • Déploiement : Kubernetes + load balancing

Justification Python : Excellente pour prototypage rapide, écosystème IA mature (owlready2, transformers, OpenAI SDK), adéquat pour MVP pédagogique (≤1000 corrections/jour).

🎯 Vue d'ensemble Technique

Ce système repose sur une approche hybride Ontologie OWL + LLM combinant :

  • Raisonnement symbolique (relations hiérarchiques, logique médicale déterministe)
  • Compréhension sémantique (flexibilité linguistique, robustesse aux variations)

⚖️ Étape 3: Scoring Pondéré

Formule de Calcul

$$ \text{Score Global} = \frac{\sum_{i=1}^{n} (w_i \times s_i \times c_i)}{\sum_{j=1}^{m} w_j} $$

Où:

  • $w_i$ = Poids du concept $i$ (défini par catégorie)
  • $s_i$ = Score du match (0-100%)
  • $c_i$ = Coefficient catégorie (rhythm: 1.2, conduction: 1.1, etc.)
  • $m$ = Nombre total de concepts attendus

# Bonus si diagnostic principal identifié (poids >= 3)
has_diagnostic_principal = any(

    for c in validated_concepts

🔧 Composants Techniques Détaillés

1. OntologyCorrector (Simple)

Rôle: Scoring hiérarchique basique avec owlready2

class OntologyCorrector:
    def __init__(self, owl_path):
        self.onto = get_ontology(owl_path).load()
        self.concepts = {}  # label → class mapping
    
    def get_score(self, expected, user_input):
        # Logique hiérarchique pure
        if user_cls == expected_cls: return 100
        elif user_cls in expected_cls.ancestors(): return 50  # Parent
        elif expected_cls in user_cls.ancestors(): return 25  # Child
        else: return 0

Limitations:

  • Pas de synonymes
  • Pas de nuances sémantiques
  • Strict matching sur labels

2. SemanticScorer (Avancé)

Rôle: Scoring sémantique avec LLM

class SemanticScorer:
    def _compare_concepts_llm(self, student, expected):
        """Utilise GPT-4o pour comparer sémantiquement"""
        
        prompt = f"""
        Compare ces deux concepts ECG:
        - Étudiant: "{student['text']}"
        - Attendu: "{expected['text']}"
        
        Retourne JSON:
        {{
          "match_type": "exact|parent|child|sibling|contradiction|extra",
          "score": 0-100,
          "explanation": "..."
        }}
        """
        
        response = openai.ChatCompletion.create(
            model="gpt-4o",
            messages=[{"role": "user", "content": prompt}],
            temperature=0.1,  # Déterministe
            response_format={"type": "json_object"}
        )
        
        return parse_json(response)

Avantages:

  • Comprend synonymes ("QRS fins" = "QRS normal")
  • Gère nuances cliniques
  • Robuste aux variations d'expression

# Calcul score pondéré
category_weights = {

    'morphology': 0.9   # QRS normaux: 100 × 0.9 = 90 points

max_score = 120 + 110 + 90 + 90 = 410

🎓 Points Clés

1. Approche Hybride Symbolique + Neuronal

Symbolique (OWL):

  • Relations hiérarchiques explicites
  • Raisonnement déductif (ancestors, descendants)
  • Interprétabilité totale

Neuronal (LLM):

  • Compréhension sémantique flexible
  • Robustesse aux variations linguistiques
  • Généralisation hors vocabulaire

2. Separation of Concerns

Module Responsabilité Déterministe?
LLM Extractor NLP: Texte → Concepts Non (température > 0)
Semantic Scorer Matching sémantique Semi (température faible)
Scoring Engine Calcul score pondéré Oui
Feedback Service Génération texte pédagogique Non (créativité)

3. Prompt Engineering pour Determinisme

Stratégies utilisées:

  • Structured Output (JSON forcé)
  • Temperature ≤ 0.1 pour scoring
  • Few-shot examples dans prompts système
  • Validation schéma JSON

4. Gestion de l'Incertitude

# Confiances propagées dans le pipeline
ExtractedConcept.confidence = 0.95  # LLM extraction
  ↓
ConceptMatch.score = 85.0  # Semantic matching
  ↓
ScoringResult.percentage = 78.0 × (confidence_factor)

5. Scalabilité & Performance

Opération Complexité Temps moyen
Extraction LLM O(n tokens) ~2-3s
Matching sémantique O(n × m) LLM calls ~3-5s
Scoring pondéré O(n) <100ms
Feedback generation O(1) LLM call ~2s
Total pipeline - ~8-10s

Optimisations:

  • Batch LLM calls si possible
  • Cache ontologie en mémoire
  • Fallback feedback si LLM timeout

🔬 Limitations & Axes d'Amélioration

🎯 Conclusion

L'architecture du module de correction combine:

  1. NLP moderne (LLM pour extraction flexible)
  2. Raisonnement symbolique (OWL pour logique médicale)
  3. Scoring pondéré (métriques pédagogiques expertes)
  4. Feedback adaptatif (personnalisation selon niveau)

Cette approche hybride offre:

  • ✅ Robustesse sémantique (LLM)
  • ✅ Interprétabilité (ontologie)
  • ✅ Personnalisation (feedback contextuel)
  • ✅ Évolutivité (ajout concepts sans retraining)

Trade-offs assumés:

  • Latence acceptable pour usage pédagogique
  • Coût LLM justifié par qualité feedback
  • Dépendance API externe (futur: modèle local)
